# 准确尾发表情包：调查结论与接入条件

初次调查日期：2026-10-02。最近复核：2026-10-03。当前开发与安装版本：0.20.17。

状态：需求保留，接口条件仍未满足。本文是设计与验收记录，不代表插件已经支持准确尾发。

## 2026-10-03 复核与下一步

0.20.16 与 0.20.17 更新的是插件管理面板，不是主聊天文字队列。
当前图库、发送设置、运行状态与独立图片详情可以保持；`core`、`services`、
`__init__.py`、业务配置默认值和主聊天发送协议没有随这次 UI 更新改动。
开发清单与已安装清单均为 0.20.17，默认仍为 `defer_tool_sends=false`。

本轮重新运行前端专项回归 22 项、隔离 Python 测试 825 项，均通过。
查看的是现有隔离验收截图，没有操作 Steam 主聊天界面；
这些结果验证现有功能，不能证明准确尾发已经可用。

另外复核了几条看似可能绕过限制的路径：

- 工作区的主工具远程回调传递 `name/arguments/call_id/raw_arguments`；
  插件回调只将 `arguments` 交给处理器，没有为该路径注入可靠的原回复定位句柄。
  传输请求 ID、模型工具调用 ID 与聊天回复 ID 不是同一种身份。
- Steam 的 `appendReactChatBlocks` 将插件图片创建为新的 system 消息；
  `request_id` 只参与消息 ID 前缀，没有传入原回复锚点或尾部排序参数。
  底层聊天组件支持排序，不等于插件投递路径公开了该能力。
- 工具结果信封的 `images` 通道用于模型视觉输入，不是主聊天的尾部附件。
  改走该通道会违背主聊天自产图片不反灌模型的 `blind` 纪律。

下一步优先请求宿主提供**绑定原回复的有序尾部附件投递能力**，
而不只是新增“模型完成”通知。宿主掌握真实文字队列，可以在同一队列中安排附件，
避免插件收到完成通知后另行 push 与下一轮输出竞争。
这种接口可以由宿主内部完成排序，不要求插件读取聊天正文、修改 DOM 或监听浏览器事件。
它仍然需要宿主提供新能力，不能由管理面板 UI 更新代替。

具体的需求、兼容边界和验收场景已整理为
[宿主接口需求草稿](host-reply-tail-request.md)。
该草稿仅保存在插件仓库，尚未提交到外部，也没有修改宿主。
宿主未提供可验证的接口前，不制作声称支持准确尾发的新包。

## 目标与当前决定

猫娘可以在回复过程中选好表情包，但图片应排在原回复的全部正常文字之后。
发送由实际回复收尾驱动，不使用固定延迟、按字数估算显示时间或随机补图。
普通回复继续走猫娘自己的文字通道，不搬进工具配文，不伪装为插件文字气泡。

保持只改插件、不修改宿主或 Steam 安装文件的边界。
目前保留 0.20.17 沿用的 0.20.15 主聊天即时发送，默认 `defer_tool_sends=false`。
不重新开启旧版日志排队，不修改积极度、提醒节奏、冷却、去重或概率，
也不为了调整位置而减少模型调用工具的机会。

## 已核实的限制

插件的 `services/sender.py` 目前在主聊天工具选图后直接提交图片，
所以剩余正常文字可能出现在图片之后。
可选的 `services/turn_end.py` 只读主日志完成记录，并用健康接口检查后端忙态；
它不知道前端还剩几段文字，也没有工具调用与原回复之间的可靠话轮标识。

本次不仅检查了工作区宿主源码，也核对了 Steam 实际安装版前端：

- `static/app/app-chat-adapter.js` 的 `processRealisticQueue` 在消息合并关闭时，
  根据上一气泡的显示时刻等待，使相邻文字气泡至少间隔 2000 毫秒。
- `static/app/app-websocket.js` 的 `flushRealisticBufferOnTurnEnd` 将剩余文字加入队列，
  调用异步队列处理，但不等待队列排空。
- 浏览器内部 `neko-assistant-turn-end` 在该处理后发出，仍不是文字队列排空回执。
- `appendReactChatBlocks` 收到插件图片后追加独立消息，没有将图片附着到原回复末尾的接口。

因此，“模型生成完成”“后端发送结束”“最后一段文字已经显示”是不同的事件。
`turn_end analyze check`、`is_responding=false`、`audio_done` 和语音播放结束，
都不能单独证明所有文字气泡已显示。

宿主工作区的 `main_logic/lifecycle_bus.py` 是会话进程内总线，
没有向插件子进程开放该生命周期通道。插件公开的 lifecycle 总线用于插件生命周期，
不能仅凭名字相同就把它当成聊天回复生命周期。
较新源码中的会话记录读取能力同样不构成前端呈现确认，
也不能据此假定 Steam 冻结后端已经支持。

## 外部参考可借鉴的机制

参考插件的 `mixins/event_handlers.py` 使用框架提供的本轮事件对象保存选图：
非流式回复在结果装饰阶段准备图片，再由 `after_message_sent` 分离尾发；
流式回复在 `STREAMING_FINISH` 处理阶段尾发。
它借助回复生命周期的因果关系，不通过日志结束后再等几秒猜测发送时机。

可借鉴的是“选择、等待完成、认领发送、清理”的分工，
以及状态归属于原回复，而不是仅因最新话轮变化就撤销已完成回复的配图。
不能直接复制这些钩子名称，也不能把定时器包装成同等的发送后钩子。
参考实现本身没有跨宿主的显示确认或任意并发下的严格一次交付保证。

## 开始实现前的接口条件

以下是期望宿主提供的契约，不是现有 API，也不是本次修改宿主的计划。
若宿主直接提供有序尾部附件接口，文字完成与排序可以由宿主内部完成，
不必另外公开前端完成事件；但仍须明确原回复身份、终态、取消与交付状态。

1. **可靠关联原回复**：原工具调用与完成事件能对应到同一角色、会话和请求或话轮。
   插件自行生成一个 UUID、猜测最新角色回复或读取日志时间，不能代替这种关联。
2. **可验证的文字完成**：信号表示原回复全部文字气泡已经提交呈现，
   包括分段队列最后一项，而不只是模型不再生成。
3. **有顺序保证的图片投递**：宿主支持把待发附件放在原回复文字末尾，
   或者完成通知与尾部附件发送处于同一有序流程。
   仅在收到完成事件后由插件另行 push，仍可能与下一轮输出竞争，
   不能据此承诺图片始终紧随原回复。
4. **明确的结束原因**：正常完成、用户打断、会话关闭和失败可区分，
   重复或过期事件不会被解释成另一轮回复完成。
5. **Steam 兼容证明**：实际安装版提供并验证上述能力，接口不可用时保留即时发送，
   不自动回退为固定等待，也不挂住工具等待回复结束。

在这些条件满足前，不添加空的发送抽象、未接入的事件监听或新的默认排队模式。

## 接入后的插件行为

工具选图时只准备并登记本轮图片，立即返回真实的排队回执，让正常回复继续。
节奏判定只执行一次，不在收尾时再次掷骰或重新选图。
状态仅存内存，关闭或重启后不补发旧图。

正常完成时通过原回复的有序尾部投递入口认领一次发送；
重复完成通知不得导致重复图片，也不得重复计数。
已经正常完成的回复，不仅因后来出现用户输入就撤销配图；
投递位置由宿主顺序契约保证，不能等到新一轮结束才把旧图补进去。
真正中断的原回复按明确的取消事件处理，不将图片转移到无关回复。

实际投递前重新验证插件启用状态、图片文件、图片启停和激活区。
主聊天图片继续使用 `ai_behavior="blind"`，GIF 保留原字节。
面板试发、后台 Agent 路由隔离和普通文字回复通道保持不变。
冷却、使用次数和成功台账只在图片提交到传输后更新；
传输接受不等于界面已展示，失败或部分提交必须如实报告，
没有确认与去重契约时不自动重试。

## 验收清单

以下是未来实现必须通过的验收，不是本轮已经执行的测试结果。

- 消息合并开、关两种模式下，短回复和多段长回复的图片都位于原回复文字末尾。
- 模型很早调用选图工具时，工具及时返回，普通文字仍完整输出。
- 原回复完成与下一轮输入、下一轮输出竞争时，图片不插入新一轮中间，也不无故丢弃。
- 真正打断、关闭会话、切换角色时，不把旧图发送到无关回复或角色。
- 多角色、重复完成事件、并发收尾和重复工具调用不导致重复投递或计数。
- 接口缺失或不兼容时保留稳定即时路径，不依赖计时器猜测显示完成。
- 图片删除、禁用、激活区变化、插件关闭、上传失败和传输拒绝有明确结果。
- 原有冷却、去重、概率、主工具注册与 Agent 隔离测试继续通过。
- GIF 动画和主聊天 `blind` 行为保持，重启不补发排队图片。
- 使用实际 Steam 界面观察消息顺序，不能只凭日志或模拟传输宣称尾发成功。

达到接口条件后再制作新的 `.neko-plugin` 测试包，由用户导入 Steam 验收。

后续 0.20.16 / 0.20.17 是独立的 UI 更新，不表示准确尾发已经实现。
2026-10-03 本轮只复核与更新文档，不升级版本、不重打包，也不自动安装到 Steam。
