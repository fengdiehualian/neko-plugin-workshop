### 那 38 个人工合并文件集中在哪

它们几乎全是**卡牌/伤害/能量 Hook 的镜像（Mirrors）**与**模拟状态**——正是"直接读写游戏私有成员"最密集的地方，所以也正是改编最集中的地方：

- `Engine/InCombat/Mirrors/Hooks/Card/*`（13 个）：抽牌、消耗、生成、打出前后、打出次数、费用修改、可打出判定…
- `Engine/InCombat/Mirrors/Hooks/Damage/*`（3 个）、`Hooks/Block/*`、`Hooks/TurnEnd/*`
- `Engine/InCombat/Mirrors/Cards/*`、`Mirrors/Orbs/*`、`Mirrors/Enchantments/*`
- `Engine/InCombat/Simulation/*`（3 个）：`CombatPredictionSimulator` 与卡牌扩展
- `Prediction/*`（4 个）：卡效注册表、死亡能力、怪物行动、遗物预测状态
- `Runtime/CombatRootSnapshot.cs`、`Runtime/ContinuationStamp.cs`
- `Search/SimulatedCombatState*.cs`（4 个）、`Search/CombatBeamSolver.StateEvaluation.cs`、`Search/CombatBeamSolver.Phases.cs`

其中 **30 个含 GameRef 反射调用**（合并时要保证上游的新逻辑同样走反射）。完整清单由 `sync-vendor.ps1` 每次生成。

## 四、能力差距（自 0.28 起上游做了什么）

上游自 0.29 到 0.50.1 共 **84 个版本、约 9.6 万字符**发布说明。变化集中在：卡牌规则（46 个版本涉及）、药水（31）、预测（25）、内存与 GC（23）、选择处理（22）、搜索（18）、性能（16）。

### 你可以直接受益的几类（挑上游自己写明、且能读懂的）

**求解正确性（最重要）**

- **0.42.0**：修复"战斗中全域历史不同却被当成同一状态合并"的问题——涉及 Gold Axe、Voltaic、Tear Asunder、Pull From Below、Murder、Supermassive 这类**依赖整场累计计数**的卡。这类错误会直接让搜索选错路线。
- **0.44.0**：修复两类**计算失败**——回合开始生成的卡触发 Power 变化时路线计算崩掉；智能用药插入"格挡药水"改变了卡牌状态或提前结束战斗时崩掉。
- **0.48.0**：把"基于已知治疗来源的路线剪枝"**扩展到全部五个角色与所有原版敌人**（来源：PR #188/#199/#200）。高损血路线的无谓搜索大幅减少。
- **0.49.0 / 0.49.2**：一大批预测与结算顺序修复（多段获得时的效果预测、结束回合与自动打牌的顺序、能力强制结束回合后的知识/能力状态等）。
- **0.44.0（PR #123）**：改进**重复出牌循环**的计算，并把这些循环按"重复次数"归组展示。

**性能与内存**

- **0.42.0**：低内存余量下的行为改善；限制超长搜索中保留历史状态的增长。
- **0.42.0 / 0.48.0**：减少卡牌目录的重复查询；**把续用数据的创建推迟到路线被选中之后**。
- **0.44.0（PR #124/#125）**：找到完整胜利路线后**更早停止**追加搜索；减少路线计算中的冗余工作。

**新能力**

- **0.42.0**：新增可选设置「**预知战后药水奖励**」（默认关闭）；路线摘要现在区分"本场已用掉的药水 / 路线还计划用的药水 / 预测的奖励药水"。
- **0.48.0**：新增「**本场保留全部战斗日志**」选项（缺陷报告页面），用于排查。
- **0.49.2**：增强**未知模组识别**（例如 BetterVanillaSTS2），对未登记模组显式提示"未适配、无法求解"，而不是静默算错。

> 这些是从发布说明里提炼的**要点**，不等于全部差异。逐版本清单见上游 `docs/releases/`。

| Shim 修正（`EntryShim` / `SolverPolicyEnums`） | 小 | 上游把部分声明挪进了可 vendor 的文件，规则里的 3 条重复错误会自动消失或需微调 |
| 编译迭代到零错误 | 若干轮 | 机器可判定 |

### 风险

1. **语义回归不可在此验证。** 求解器决定出牌，一次静默的行为变化可能让胜率变差而日志正常。**必须游戏内实测。**
2. **上游要求 RitsuLib ≥ 0.6.0**，本仓库 README 写的是 0.5.18+。两边都指向同一个创意工坊条目（`3747602295`），实际用的是 Steam 已装版本，但**目标游戏 API 版本必须一致**（两边都是 0.111.0）。升级前值得确认 RitsuLib 版本。
3. **一次跨 84 个版本的跳跃**，中间没有任何过渡验证点。若出问题，二分定位会很困难。**建议备选方案：分几段跳**（例如先到 0.36 附近，再到 0.44，最后到 0.50.1），每段都能编译+实测。
4. **回滚依赖 git。** `-Apply` 会另存一份 zip 备份，但真正的回滚手段是 `git checkout -- game_mod/nekospire/Solver`。

## 六、建议的推进方式

### 先纠正一个直觉错误：分段跳**更贵**，不是更稳

我起初倾向于建议"分几段跳、每段实测"。把成本真的算出来之后，这个建议是错的：

| 方式 | 需人工合并（次） | 新增文件 | 说明 |
|---|---:|---:|---|
| **一次性跳** `v0.28.0 → v0.50.1` | **38** | **542** | 每个改编文件只合并一次 |
| 分三段：`0.28.0→0.36.0` | 33 | 149 | |
| 　　　　 `0.36.0→0.44.0` | 22 | 248 | |
| 　　　　 `0.44.0→0.50.1` | 24 | 304 | |
| **三段合计** | **79** | **701** | 同一文件在每个边界重复合并，且要分三轮重新适配 + 重新验证 |

**分段唯一的收益是"每步爆炸半径小、可以在游戏里逐段验证"；代价是合并工作量约翻倍。** 所以：

| 方案 | 内容 | 适用 |
|---|---|---|
| **A. 一次跳到 0.50.1（推荐）** | 一轮做完，编译到零错误后交给你实测。合并面最小（38 个文件） | 默认选择 |
| **B. 分段跳** | 只有当你想在**每段之间进游戏实测**、并且愿意付约两倍的合并工作量时才用 | 对风险极度保守 |
| **C. 定向摘取** | 不追版本号，只把"求解正确性"清单里的某几项（如 0.42.0 的全域历史修复、0.48.0 的治疗剪枝扩展）移植过来 | 只想修掉具体毛病 |

无论哪种，第一步都一样：**先跑只读报告**（`game_mod\scripts\sync-vendor.ps1`），确认规则判定与你的意图一致。

### 无论选哪个，真正的安全网是这两条

1. **git 分支 + 提交**。写代码前先 `git checkout -b sync-combat-solver-0.50.1`，让回滚只花一条命令。
2. **游戏内实测**。这是唯一能发现语义回归的手段；编译通过和测试通过都**不能**替代它。
